## 二、自动投稿模块架构回顾

`app/autopost.py` 是一个常驻守护线程，按 `scan_secs`（默认 30s）轮询监视目录，把录完的视频自动套模板入队：

```
_loop（每 30s 唤醒一次）
  └─ scan_once
       ├─ _recheck_queued     重判定「源文件已变化」的在队任务
       └─ 逐规则 _scan_rule
            ├─ _candidates    os.walk 遍历目录 + 每文件 os.stat
            ├─ autopost_is_seen  每文件一次 SQL（LEFT JOIN seen×tasks）   ← 瓶颈①
            ├─ _stable        大小+mtime 静默期判定
            └─ _ingest_group
                 └─ _probe_ready 每文件一次 ffprobe 子进程（串行）        ← 瓶颈②
```

入队后由 `worker.py` 单线程上传，成功后回调 `archive_originals` 归档原件。

---

## 三、瓶颈定位（数据驱动）

用基准脚本模拟 3 条规则、每条 600 个视频文件（590 个已 seen、10 个新录制），统计单轮扫描的系统调用次数：

| 指标 | 优化前（稳态轮） | 说明 |
| --- | --- | --- |
| `seen` 判定 SQL | **1800 次/轮** | 每个候选文件一次 `SELECT ... LEFT JOIN`，大库下 O(N) 次 SQL |
| `os.stat` 调用 | **1806 次/轮** | `os.walk` 列目录后又对每个文件 `stat` 一次 |
| `ffprobe` 子进程 | 稳态 0，入队轮 1770 次 | 多分P稿逐个串行探测；同一文件跨轮重复探测 |

**结论**：大录播库（数千文件）长期无人值守时，每 30 秒就要做数千次 SQL + 数千次 stat，CPU/磁盘 I/O 被无谓消耗；多分P稿入队时 ffprobe 串行启动成为主要延迟。

## 四、已实施的优化（4 项）

### 优化 1：批量 seen 判定，N 次 SQL → 1 次

- **改动**：`store.py` 新增 `autopost_seen_batch(paths)`，用 `WHERE path IN (...)` 一次查出所有候选的 `{size, mtime, status}`（自动按 900 分批规避 SQLite 变量上限）；`autopost.py` 新增 `_seen_from_row()` 在内存里复刻原判定语义，`_scan_rule` 一轮只查一次。
- **收益**：每轮 SQL 从 **1800 → 0**（稳态轮完全不查，候选已被批量判定过滤）。
- **兼容**：判定语义与原 `autopost_is_seen` 完全一致（活动任务无条件占位、终态按签名比对）。

### 优化 2：os.scandir 合并目录遍历与 stat

- **改动**：`_candidates` 用显式栈 + `os.scandir` 递归替代 `os.walk`，直接用 `DirEntry.stat(follow_symlinks=False)`（Unix 上复用 scandir 缓存的 lstat），省掉「列目录 → 再 stat」的第二次系统调用。跳过隐藏目录、归档目录、临时后缀、非视频文件的语义保持不变。
- **收益**：稳态 `stat` 调用从 **1806 → 6**（-99.7%），稳态耗时 **0.053s → 0.025s**（-53%）。

### 优化 3：ffprobe 结果缓存 + 并行探测

- **改动**：
  - 新增 `_probe_cache`（按 `path` 存 `size/mtime/info`），只缓存「成功读出时长」的完整容器；签名变化自动失效，正在录制（duration=0）的文件绝不缓存。
  - `_probe_ready` 命中缓存直接返回，省掉子进程。
  - `_ingest_group` 对未缓存的文件改用 `media.probe_many` **并行**探测（默认 4 workers），并用 `zip` 保序。
  - `scan_once` 末尾清理失效缓存，并设 5000 条上限防止内存膨胀。
- **收益**：重复探测的 ffprobe 调用 **200 → 0**（-100%）；20 分P并行探测 **1.019s → 0.256s（4.0x）**。

### 优化 4：稳健性收尾

- probe 缓存与 `_sig`/`_warned` 同步清理，避免长期运行内存泄漏。
- `_probe_cache_hit` 用 `Optional` 精确表达命中/未命中，避免 falsy 值误判。

## 五、优化前后性能对比

| 场景 | 指标 | 优化前 | 优化后 | 改善 |
| --- | --- | --- | --- | --- |
| 稳态扫描（1800 文件） | SQL 查询 | 1800 | 0 | **-100%** |
| 稳态扫描（1800 文件） | stat 调用 | 1806 | 6 | **-99.7%** |
| 稳态扫描（1800 文件） | 耗时 | 0.053s | 0.025s | **-53%** |
| 重复探测（200 文件） | ffprobe 调用 | 200 | 0 | **-100%** |
| 多分P入队（20P） | 探测耗时 | 1.019s | 0.256s | **4.0x** |

> 数据量越大、分P越多，收益越明显；小库（几十个文件）下优化几乎无感但无副作用。

## 七、进一步优化建议（未实施，供参考）

按投入产出比排序：

1. **增量扫描替代全量轮询**：当前每轮仍遍历所有文件。可用 `watchdog`（inotify/FSEvents）监听目录事件，只在文件新增/变更时触发判定，把「每 30s 全扫」变成「事件驱动」，稳态 CPU 接近 0。代价是需要处理事件丢失与首次全扫。
2. **多规则并行扫描**：`_loop` 里规则串行处理，一条规则的大目录会拖慢其它规则。可用线程池并行 `_scan_rule`（注意 `_sig`/`_status` 的锁粒度）。
3. **`_recheck_queued` 的按需触发**：当前每次 `scan_once` 都调用，即使没有「源文件已变化」的任务。可以让 `autopost_recheck_needed()` 为真时才调用（该接口已存在）。
4. **静默期与扫描相位对齐**：`_stable` 要求 `now - mtime >= need`，录制完成后最快也要等一个静默期才入队；可引入「录制完成事件」提前进入候选，牺牲一点保守性换实时性。
5. **probe 缓存持久化**：缓存目前仅在内存，服务重启后需重新探测。可把时长信息写入 `autopost_seen` 或单独的轻量表，重启后直接复用。
6. **标题模板占位符扩展**：当前支持 `{文件名}/{日期}/{主播}`，可增加 `{时长}/{分辨率}` 等（probe 已有这些数据），满足更灵活的命名需求。
