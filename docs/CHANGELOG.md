# 演进与关键设计（v98 → v106）

> 本文档记录本项目的核心演进与关键设计，便于接手维护。代码版本以 `app/server.py` 中的 `APP_VERSION` 为准（当前 **v106**）。

## 〇、v106 要点（2026-11-14）：额度即时占位 + 入队即刻刷新

**问题一：投稿完成后额度刷新有延迟，下一个稿件可能越界。**
根因是额度只在「投稿成功之后」记账：一次投稿从开始上传到拿到结果要几分钟，
这段时间B站创作者中心（`member.bilibili.com/x/web/archives`）里根本查不到这篇稿，
额度判定却发生在「下一篇开始之前」，于是按旧数字一路放行，直到越界。

- 账本改成分状态记账（`ledger.py`）：**上传一开始就写 `inflight` 占位**，成功后
  `confirm` 成 `confirmed`（带上 BV/aid），`release` 撤回确定没投出去的失败，
  `mark_uncertain` 保留「已进入提交阶段后失败」的占位（见下）。
- `worker.py` 在 `official.publish()` 之前 `ledger.reserve()`，成功 `confirm()`；
  异常时按本轮到达过的最深进度分流：`SUBMIT_PROGRESS_MARK = 0.9`（官方通道
  提交阶段为 0.92）之前失败 → 撤回占位；之后失败（提交响应超时、进程中断）→
  保留 `uncertain`，因为稿件可能已经发出去了。
- `_mark_interrupted()` / `shutdown()` 用任务落库的进度做同样判断，进程重启也不会
  凭一份「还没有这篇稿」的旧列表放行。
- `start()` 与「清空已结束任务」「删除任务」都会 `ledger.reconcile()` / `release()`，
  孤儿占位不会白占 24h 额度。
- 修正账号桶归一：`quota.check_quota()` 过去把 `account_key=""` 原样透传，读的是空桶，
  而 `worker` 写账本写的是「生效账号」桶——未确认永远算成 0。现在空串一律归一到
  `active_account_id()`。
- `/api/tasks` 的响应指纹加入 `count/pending`：账本变了而任务状态没变时也会重建响应，
  界面上的额度数字不会停在旧值；额度提示会注明「其中 X 篇上传中/结果未知」。
- 额度缓存键三种写法（账号 id / 生效账号 / `_active`）全部清掉，避免 180 秒旧数字。

**问题二：加入任务后队列不会立刻刷新显示任务。**
`pollTasks()` 开头有「上传文件时不抢带宽」的短路 `if (state.uploading) return;`，
而提交完成后的那次 `await pollTasks()` 又发生在 `finally` 把 `state.uploading = false`
之前——于是本次刷新被自己短路掉，用户要等下一轮自然轮询（退避后最长 20 秒）才看到任务。

- `pollTasks(force)` 增加 force 参数，上传期间的强制刷新可以穿透守卫。
- 新增 `prependTasks()`：`/api/publish` 返回的任务**本地立刻插到队列顶部并重绘**
  （多文件逐个入队，每传完一个就显示一个），不等服务端轮询。
- `finally` 里先 `state.uploading = false`，再 `await pollTasks(true)`。
- 队列里有 `uploading / queued / waiting_schedule` 任务时不再退到 10/20 秒轮询
  （最多 5 秒），投稿完成那一刻也能马上看到。
- 新增 `tests/verify_v106.py`（28 项）：账本状态机、模拟B站入库延迟下的越界验证、
  账号桶归一、缓存即时 +1、worker 三种收尾、前端守卫与版本号同步。

## 〇.一、v105 要点（2026-11-13）：移除 biliup，固定单通道

**动机（安全性修复）**：biliup CLI 使用其自带的 `cookies.json`（内含 app `access_token`），与网页 Cookie 可能不是同一个 B站 账号。若两者不一致，稿件会静默投到**另一个账号**，而额度、风控、统计仍按本号计算，完全不受监控——风险不可接受。

- **删除** `app/channels/biliup_cli.py` 及 `worker.py` 中的通道选择/实体校验逻辑。
- `worker._choose_channel()` 固定返回 `"official"`，保留函数壳以兼容调用点与回归测试；上传直接调用 `official.publish()`。
- `server._public_config()` 过滤所有 `biliup_*` 键并强制 `channel = "official"`；`/api/bootstrap` 不再下发 `env.biliup`；`/api/config` 白名单移除 biliup 相关项。
- `store.DEFAULT_CONFIG` 移除 biliup 配置段。
- 前端设置面板移除上传通道选择、biliup 可执行文件/线路/登录态等控件，保留「上传线路（CDN）」选择。
- 新增 `tests/verify_ui_v105.py`：校验前端资源无 biliup 字样、bootstrap 只下发 official、设置面板控件已移除、保存无 JS 报错。
- **升级兼容**：历史 `config.json` 里残留的 `biliup_*` 键被忽略，不会被下发或误用，无需手工清理。

## 〇.二、v103 要点（2026-11-12）

- **状态通知（Webhook）**：新增 `app/notify.py`，在队列执行器四处插入 `_notify()`（稿件终态 / 额度封禁暂停 / 封禁解除续投 / 限流卡住）。不填地址完全不触发；独立守护线程 + 6s 超时，失败绝不阻塞队列；支持企业微信/钉钉/飞书/Server酱/Telegram/通用 JSON。详见 `docs/V103-webhook-auth.md`。
- **Web 访问鉴权**：新增 `@before_request` 中间件 + `config.web_auth`，支持 Token / Basic Auth，默认关闭、凭据不全不拦截，仅 `/api/health` 豁免。
- **定时阈值修正**：B站定时实际只需提前 5 分钟，`SCHEDULE_MIN_AHEAD` 由 4h30m 改为 **10 分钟**。
- **文案清理**：删除旧版「达到上限+1 触发封禁」冗余说明；「定时稿件过期」限定为「本地定时稿件」。

## 一、这是什么

一个**跑在自己电脑上的 B站投稿面板**（本地 Flask 服务 + 浏览器单页前端）。把视频拖进浏览器、填标题/分区/标签、排进队列，软件按**单线程顺序**帮你投出去，带进度、日志、失败重试、24h 额度把关、定时发布、多分P、合集、话题、仅自己可见、扫码登录等能力。

- 多账号：可登记多个 B站账号，按任务指定投放账号，额度/节流/风控**按账号隔离**。
- 单一上传通道：内置官方接口（无需额外软件）。v105 起移除 biliup CLI，见第〇节。
- 私有：Cookie 只存在本机 `data/config.json`（权限 0600），不上传任何地方。

## 二、核心架构

| 层 | 模块 | 职责 |
|---|---|---|
| 入口 | `run.py` | 解析参数、启动 `create_app()`、注册退出收尾（`worker.shutdown` 把 uploading 标为已中断）、SIGTERM 转 SystemExit |
| Web | `server.py` | 所有 HTTP 接口 + 静态页；维护**统计缓存**（workbench 按统计日缓存 / archive 90s 缓存 + 投稿作废）、**响应体指纹缓存**、图床代理、账号头像预热 |
| 队列 | `worker.py` | 单线程 `_loop` 顺序取任务；负责 10 分钟窗口节流、风控/限流冷却、**24h 额度把关与封禁等待**、定时稿调度、卡死看门狗、合集后台挂载 |
| 额度 | `quota.py` | `nav` 登录态、创作者中心三状态并发拉取、账本合并、封禁状态机 `quota_ban_until` |
| 账本 | `ledger.py` | 每次投稿成功即落地一条（带 BV/aid 身份键、按账号分桶、保留 26h），填补 B站列表入库延迟 |
| 存储 | `store.py` | `config.json`（含多账号 + 迁移自愈）+ `publish.db`（WAL）+ 模板；配置/任务指纹缓存 |
| 通道 | `channels/` | `official`（bilibili-api-python）唯一通道；v105 起固定为 official |

**设计要点**：用单线程顺序上传是刻意的（B站同账号并发不友好，也避免额度统计打架）；所有阻塞等待都走可中断 `Event.wait`，取消/暂停能立刻生效；进度落库按「≥1s 或 ≥1%」节流，避免分块回调压垮 SQLite。

## 三、投稿主流程（`worker._handle`）

1. **定时稿分流**：`local` 本地候到点自动上传；`bili` 距发布 ≥10 分钟交 B站定时、不足则本地候到点、超 15 天直接 fail、过期超阈值按设置拦下。
2. **10 分钟窗口节流**：按**账号**独立计算（A 占满窗口不拖 B）；占满则登记该账号为「暂时跳过」，主循环改取别的账号。
3. **24h 额度把关**：复用 10s 内新鲜结果或现查。三种分支：**未登录 → fail**；**数据不全且非封禁期 → 人工暂停**；**额度满/封禁 → 自动暂停排队（留 queued，不标红）**。
4. **补齐封面**：无封面则从首视频抽帧；抽不到 → fail。
5. **上传**：v105 起固定走内置官方接口（`_choose_channel()` 返回 `official`），不再做通道探测。
6. **上传 + 记账**：成功后立刻写账本（未确认 +1）、记节流窗口、清限流冷却；成功后异步挂合集（后台单线程，不卡主队列）。
7. **失败处理**：限流（-702/406/429）与风控（-352/-796/-412/验证码）分两类，前者等 1/10 分钟自动续投**不消耗重试次数**，后者按账号冷却；连续限流达阈值 → `rate` 暂停待人工；其它异常按 `max_attempts`（默认 2）重试。

## 四、24h 投稿封禁规则（重点）

**真实规则**：近 24h 投稿数一旦达到 **n+1**（上限 50 即 51）→ B站**封禁投稿**；封禁期内即使老稿滑出、额度降到 n 以下**也不能投**，必须等窗口内稿件全部过期、**额度归 0** 才恢复。

因此「封禁 24 小时」与「额度归零」在数据上等价，截止时刻取 **`max(ctime) + 24h`**（最新一篇投出时触发 n+1，从它起算 24h 后全部过期）。

### 封禁状态机（`quota.quota_ban_until`）

| 状态 | 触发 | `ok` | 恢复条件 |
|---|---|---|---|
| 正常 | `count < limit` | True | — |
| 刚好满 n | `count == limit` | False | 等最早一篇滑出，`next_release_at = min(ctime) + 24h` |
| **封禁** | `count > limit`（n+1） | **False（恒定）** | `count == 0`，即 `max(ctime) + 24h` |

**关键实现约束**（最易漏处）：

- 封禁截止 `quota_ban_until` **落盘到 config**，重启/升级/接口抖动都不丢、不误放行。
- 封禁期内 `check_quota()` 的 `ok` 恒为 False，**不看当前 count 是否已降到上限以下**。
- 只有 `count == 0` 才清除封禁；名义截止已过但稿件还在时**顺延 60s 复查**，不误放行也不永久卡死。
- 接口抓不全（`incomplete`）时**沿用旧封禁值**，不新设也不清除；宽松模式/异常分支同样不能绕开。
- `worker._quota_with_ledger()` 缓存合并后**必须再过一次封禁判定**，否则 `count < limit` 会把封禁覆盖成放行。

## 五、「额度恢复后自动继续投稿」开关

设置 →「额度与重试」→ **额度恢复后自动继续投稿**，对应配置 `auto_resume`（默认开启，`/api/config` 白名单内）。

### 暂停原因分型

| 原因 | 谁写的 | 自动恢复 |
|---|---|---|
| `""` | 运行中 | — |
| `manual` | **用户主动点暂停** / 额度统计不完整待核对 | ❌ 绝不自动开投 |
| `boot` | 部署/升级时写入的保护性暂停 | ✅ 受 `auto_resume` 控制，开启即自动解除 |
| `quota` | 额度满 / 24h 封禁自动暂停 | ✅ 到解封时刻自动复查续投 |
| `rate` | 连续限流待人工核对 | ❌ 需人工点继续 |

**原则：用户主动的暂停永远优先。** 开启 `auto_resume` 只解除部署保护性的 `boot` 暂停，不会把用户自己按下的 `manual` 暂停悄悄解除；手动暂停落盘，重启后依然是暂停。

### 启动自动恢复链路

`start()` → 读 `paused_reason` → 若为 `boot` 且 `auto_resume` 开 → 清 `boot` 保护 → worker 现查额度 → 检测到封禁 → `pause_for_quota()` 转 `quota` 等待，落盘 `quota_resume_at` → 到点复查额度归零即 `pause(False)` 续投。

## 六、前端变化

- 红色**封禁横幅**（`data-mode="ban"`）：说明达到上限+1、封禁期内额度下降也不能投、需等额度归零、显示排队数与解封倒计时、无需人工值守。
- 蓝色 `quota` 横幅保留，用于「刚好满 n、等一篇滑出」；限流橙黄 `rate` 横幅优先；深色主题均适配。
- 额度胶囊、提交成功提示同步改为封禁语义；`APP_VERSION` 随版本递增，静态资源带 `?v=` 版本号防缓存。
- 设置面板含 `autoResume` 开关（读写 `auto_resume`）。

## 七、部署与备份

- 数据库是 **WAL 模式**：只复制 `publish.db` 会丢 `publish.db-wal` 里的新任务，**备份/迁移必须整目录复制**（`publish.db` + `publish.db-wal` + `publish.db-shm`）。
- 部署时通常会在 `data/config.json` 写入保护性 `paused_reason: "boot"`，配合 `auto_resume: true` 让启动后自动恢复（检测到封禁则转入 `quota` 等待）。

## 八、已知限制

- 队列单线程顺序上传，未做并发。
- 官方接口通道依赖 `bilibili-api-python`，B站接口变动可能需升级。
- 定时发布能否用取决于账号是否具备 B站定时权限；>15 天无法定时。
- 只处理本机文件上传，不做远端拉取/转码。
- v105 起只提供内置官方接口一条上传通道，不再支持 biliup CLI。
