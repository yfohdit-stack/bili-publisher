# 演进与关键设计（v98 → v118）

> 本文档记录本项目的核心演进与关键设计，便于接手维护。代码版本以 `app/server.py` 中的 `APP_VERSION` 为准（当前 **v118**）。

## 〇、v118 要点（2026-11-26）：自动投稿扫描热路径优化

大录播库（数千文件）每 30 秒一轮扫描，原来每轮要做数千次 SQL + 数千次 `stat`，多分P稿入队还要串行起几十次 `ffprobe`。本版只动扫描热路径，上传/封面/队列/webhook/前端均未改：

- **批量 seen 判定**：新增 `store.autopost_seen_batch()`，把「每个候选一次 `SELECT … LEFT JOIN`」压成「整批 `IN (…)`」（按 900 分批规避 SQLite 变量上限），`_scan_rule` 一轮只查一次；`autopost_is_seen` 与批量版共用新的纯函数 `autopost_seen_hit()`，判定语义不再两处各写一份。
- **`os.scandir` 替代 `os.walk`**：直接复用 `DirEntry` 缓存的 lstat，省掉「列目录 → 再逐个 stat」的第二轮系统调用。跳过隐藏目录/归档目录/临时后缀/非视频的语义不变。
- **ffprobe 缓存**：`_probe_cache` 只缓存「能读出时长」的完整容器（正在录制的绝不缓存），签名 = 体积 + mtime + inode，同一路径被原地覆盖成同尺寸文件也不会命中旧时长；`scan_once` 末尾清理失效项并设 5000 条上限。
- **多分P并行探测**：`_ingest_group` 对未命中缓存的文件用 `media.probe_many`（4 线程）并行探测，结果按输入顺序对齐。
- 修复优化过程中的符号链接缺陷：`DirEntry.stat(follow_symlinks=False)` 只会取到链接自身（十几字节、mtime 是建链时间），会让指向录播文件的软链被 `min_size_mb` 误判成「太小」、超体积保护失效、静默期形同虚设；现在对软链多走一次 `os.stat` 取目标文件的真实体积与 mtime。

新增 `tests/verify_v118.py`：覆盖批量 seen 与单条判定等价（未登记/活动任务/终态同签名/终态换文件）、超过 900 条自动分批、缓存命中与三类失效、`duration=0` 不入缓存、软链取真实体积与 mtime、并行探测保序。详见 `docs/自动投稿模块优化报告-v118.md`。

## 〇、v113 要点（2026-11-20）：自动投稿六项修复 + 左侧独立视图

v112 上线后用户验收提出 6 项问题，本版全部修复：

1. **Windows 跨盘清理护栏炸异常**：`os.path.commonpath` 在录播目录与
   `DATA_DIR/uploads` 不同盘符（D:\ vs C:\）时抛 `ValueError: Paths don't have
   the same drive`，异常冒泡会把**已投成功**的稿件打成失败甚至重新排队。
   `_cleanup_files` 现在捕获 ValueError → 视为 uploads 外（跨盘必然在外部），
   跳过删除，原件与成功状态都不受影响。
2. **UI 迁到左侧导航**：自动投稿从设置抽屉整体迁出，成为与「模板」「日志」
   平级的独立视图（rail 按钮 + `viewAutopost` 区块：监视规则卡 + 运行状态卡）。
   抽屉不再臃肿；5s 状态轮询只在自动投稿视图打开时发请求。
3. **删除任务不再被投回**：v112 的 delete/clear_done 会 `autopost_unmark`，
   被删文件早过静默期，下一轮扫描立刻重新入队——「删了又出现」，坏文件还会
   循环。v113 语义反转：**删任务 = 放弃该稿**，seen 登记保留，文件不再自动
   入队；`autopost_unmark` 仅保留给未来显式「允许重新入队」操作。
4. **上传前复核源文件签名**：零拷贝引用原件，入队到上传可能隔几十分钟
   （排队/额度暂停/夜间），期间录播软件续写、用户移动/删除都会传半截文件。
   入队时把 `size+mtime` 签名写进 `files[]`（`src_size/src_mtime`），worker
   开传前 `_autopost_sources_ok` 再 stat 一次：不一致 → 退回 queued 并标
   「源文件已变化，等待重新判定」；文件没了 → 判失败（source_missing）。
  扫描线程 `_recheck_queued` 对这类任务重走静默期+probe 判定，录完后**原地**
  更新签名并同步 seen 台账（后续加固为 `autopost_recheck` 原子更新），不产生重复任务。
5. **分P按场次切段**：v112 组键 `streamer|date` 会把同天下午场+晚场硬合并。
   新增 `session_gap_secs`（默认 7200s，UI 单位小时，API 校验 600..86400）：
   同组内按相邻文件 mtime 差切段，超阈值另起一稿；断播分段（间隔小）仍合并。
   同天多稿靠组计数加标题序号（2）（3）。
6. **seen 台账定期清理**：扫描线程每小时触发一次；后续加固为只删「任务已不存在、
   created_at 超 30 天且原路径已消失」的行，原路径仍在的忽略记录不会被清理后重投。

新增 `tests/verify_v113.py`（30 项，全离线）：跨盘护栏 mock、删除不投回、
签名复核+重判定闭环（续写→拦下→静默→原地更新→可投；删除→失败）、场次切段

## 〇.〇、v112 要点（2026-11-20）：录播自动投稿（多规则监视目录）

**需求**：其它录播软件负责产生录播视频，本程序自动投出监视目录下的视频；
可选分P或单独投稿、可套用投稿模板、还在录制的文件绝不上传。

**实现**（新模块 `app/autopost.py` + `autopost_seen` 台账表 + 任务新字段 `autopost_meta`）：

- **多规则**：`config.autopost = {enabled, scan_secs, rules[]}`，每条规则独立配置
  目录/模式/模板/账号/标题模板/静默期/合并等待/最小体积；总开关 + 规则开关两级。
  常驻守护线程按 `scan_secs` 扫描，一条规则失败不影响其它规则。
- **录制完成判定**：大小+mtime 静默期（默认 120s，任一变化重置计时）+ ffprobe
  能读出时长（正在录制的容器不完整）；没装 ffprobe 退化为纯静默期。
  `.part/.tmp` 等临时后缀、隐藏文件、过小文件一律跳过。
- **分P分组**：同完整相对父目录 + 同日期（文件名里的 YYYY-MM-DD/YYYYMMDD 等，
  取不到用 mtime）为一组；组内全部录完且 `group_idle_secs`（默认 600s）内无新
  文件才入队，断播分段等齐；超过 `max_parts` 自动拆稿；同组第二批标题加序号。
- **原件零拷贝**：任务直接引用监视目录里的原件上传；投成功后 worker 回调
  `archive_originals` 把原件移入监视目录下「已投稿」子文件夹（保留子目录结构，
  重名加时间戳与递增后缀防覆盖），并逐文件同步任务 files 路径。失败/取消原件留在原地可重试。
- **清理护栏**（顺手修掉的隐患）：`_cleanup_files` 原来声称「只删程序落盘副本」
  但代码没有路径判断；现在用 `commonpath` 限定只删 `uploads/` 内的文件，
  「上传后删除/过审删除/存储清理」任何路径都不会碰到录播原件。
- **防重投**：`autopost_seen` 按 路径+体积+mtime 签名，入队即登记；删除任务
  （单删/批量清理）解除登记，文件可重新入队（**v113 已反转：删任务=放弃该稿，
  登记保留不投回**）；「已投稿」目录扫描时跳过。
- **模板套用**：分区/标签/简介/合集等整包套用；合集按目标账号解析（ID 命中→
  同名匹配→放弃挂载），不拿别号合集 ID 硬投；标题占位符 `{文件名}{日期}{主播}`；
  无封面走 worker 现有抽帧兜底；账号缺省回落当前生效账号。
- **API/前端**：`GET/POST /api/autopost`、`POST /api/autopost/scan`，bootstrap
  下发状态；设置抽屉新增多规则卡片（添加/删除规则、单独保存、立即扫描、
  待投/最近入队展示）；队列任务带「自动」徽章。

新增 `tests/verify_v112.py`（53 项，全离线）：静默期/增长重置/probe 门槛、
分P合并与等待、跨天分开、断播等齐、max_parts 拆分、模板/账号/标题、多规则

## 〇.一、v111 要点（2026-11-20）：横幅优先级——暂停态优先

**问题**：`renderRateBanner()` 里 `left > 0`（某账号限流冷却未结束）的分支排在最前，
与 v108「任何原因的暂停都要显示正确横幅」的目标冲突：

- `reason=rate`（连续限流、已全局暂停、**必须人工点「继续队列」**）时，只要冷却
  倒计时还没走完，横幅就显示「预计 X 后自动继续投稿」——这句是假的，冷藏期内
  队列根本不会自己恢复，v108 新加的红色「连续触发 B站 限流 · 队列已暂停」被整段挡住；
- `reason=cover` / `reason=quota` 时，只要还有任一账号残留未过期的 `rate_until`，
  封面/额度横幅同样被挡住，用户看到的是别的账号的冷却倒计时。

**修复**：把暂停态判断整体提到最前，冷却降级为背景信息：

- `paused` 分支先按 `pauseReason` 分派（rate 红 / cover 蓝 / quota 蓝或红 / boot、manual 灰）；
- 冷却仍存在时，在各暂停文案末尾追加「（另有账号仍在限流冷却，约 X 后解除）」，
  但**不再承诺**整条队列「自动继续」；rate 暂停明确写「需人工核对后点「继续队列」，
  队列不会自动恢复」；
- 只有「队列未暂停 + 冷却未结束」这一种情况才显示倒计时与「预计 X 后自动继续投稿」，
  因为那时确实是到点自动放行。

新增 `tests/verify_v111.py`（23 项）：从 `app.js` 按括号配对取出 `renderRateBanner`
源码，套极简 DOM/state 桩用 node 真跑 7 个场景（限流冷却、rate 暂停有无冷却、
cover/quota/manual 暂停 + 冷却残留、一切正常），断言标题/mode/文案里不出现错误承诺；
另加结构断言防止以后又把冷却分支挪回最前。

## 〇.一、v110 要点（2026-11-20）：坏封面无限循环的出口

**问题**（v107 引入封面暂停时留下的口子）：`_cover_invalid_backoff` 不消耗
`attempts`，也没有封面重试上限。一张真正损坏的封面会：

```
投 → 拒 → 整条队列停 5 分钟 → 到点自动重投 → 再拒 → ……
```

永远循环：任务一直 `queued`、`attempts` 一直是 0；期间整条队列（含其它账号、
其它稿件）全部被阻塞；每轮还各推一条 task + resume 事件，Webhook 每 5 分钟刷两条。
前端文案自己写着「若反复被拒多半是文件本身不对」，但代码里没有出口。

**修复**：

- 任务表新增 `cover_hits`（老库启动时 `ALTER TABLE` 自动补列），记录同一稿件
  被「封面不合法」拒收的次数；
- 第 1、2 次仍按原口径：整条队列暂停 `COVER_INVALID_WAIT=300` 秒，任务留 `queued`、
  不消耗 `attempts`，文案标明「第 N/3 次」；
- 第 3 次（`COVER_INVALID_MAX=3`）起直接出口：任务置 `failed`，保留原始报错与
  `finished_at`，**不再暂停队列**，主循环立刻去投其它账号/稿件；
  Webhook 只有一条 ❌ 失败推送（带账号），不再每 5 分钟刷屏；
- 「重新排队」和「更换封面」两个接口都会把 `cover_hits` 清零，换图后重新获得
  3 次机会；前端横幅补一句「同一稿件连续 3 次被拒会自动判失败，队列随即继续投其它稿件」。

新增 `tests/verify_v110.py`（31 项）：字段与老库迁移、前两次暂停且不吃 attempts、
第三次出口（不暂停、判失败、只推一条）、坏稿不堵队列、换图/重排清零、文案与版本同步。

## 〇.二、v109 要点（2026-11-19）：修复 >10P 稿件连续投稿必崩（_wait_from 越界）

**现象**：单稿 11 个分P 以上，连续投稿时稿件必定失败——第一次报
`IndexError: list index out of range`，5 秒后重试再撞一次，`attempts` 到
`max_attempts` 直接判死。

**根因**：`_wait_from()`（10 分钟窗口节流）把「超出的条数」直接当列表下标：

```python
over = len(h) + need - WINDOW_MAX      # need = 本稿分P数
return max(1, int(h[over - 1] + WINDOW_SECS - now) + 1)
```

`h` 只有 `len(h)` 条，要求 `over - 1 <= len(h) - 1`，即 `need <= WINDOW_MAX`。
一旦 `need > 10`（11P 及以上）而窗口里又有记录（连续投稿的必要条件），
下标就是 `len(h)` 或更大 → IndexError。空窗口时因 `if not h: return 0` 提前
返回，所以**首个 11P 稿件能投**，成功时 `_record_videos()` 写进 11 条记录，
之后 10 分钟内再投 >10P 必崩——正是「连续投稿必定失败」。

**修复**：

- `need` 先钳到 `min(need, WINDOW_MAX)`：窗口一次最多只能容 10 个名额，超出
  部分本来就腾不出来，等价于「等窗口里的记录全部滑出再放行」；
- 下标再做一次兜底 `idx = min(over, len(h)) - 1`，任何输入都不会越界；
- `need <= WINDOW_MAX` 时结果与旧实现逐项一致（55 组对照），不影响正常节流。

新增 `tests/verify_v109.py`（19 项）：260 种 need×窗口组合无异常、旧实现对照、
语义一致性、11P 端到端进入「节流等待」且不消耗 attempts、版本号同步。

## 〇.五、v106 要点（2026-11-14）：额度即时占位 + 入队即刻刷新

**问题一：投稿完成后额度刷新有延迟，下一个稿件可能越界。**
根因是额度只在「投稿成功之后」记账：一次投稿从开始上传到拿到结果要几分钟，
这段时间B站创作者中心（`member.bilibili.com/x/web/archives`）里根本查不到这篇稿，
额度判定却发生在「下一篇开始之前」，于是按旧数字一路放行，直到越界。

- 账本改成分状态记账（`ledger.py`）：**上传一开始就写 `inflight` 占位**，成功后
  `confirm` 成 `confirmed`（带上 BV/aid），`release` 撤回确定没投出去的失败，
  `mark_uncertain` 保留「已进入提交阶段后失败」的占位（见下）。
- `worker.py` 在 `official.publish()` 之前 `ledger.reserve()`，成功 `confirm()`；
  异常时按本轮到达过的最深进度分流：`SUBMIT_PROGRESS_MARK = 0.9`（官方通道
  提交阶段为 0.92）之前失败 → 撤回占位；之后失败（提交响应超时、进程中断）→
  保留 `uncertain`，因为稿件可能已经发出去了。
- `_mark_interrupted()` / `shutdown()` 用任务落库的进度做同样判断，进程重启也不会
  凭一份「还没有这篇稿」的旧列表放行。
- `start()` 与「清空已结束任务」「删除任务」都会 `ledger.reconcile()` / `release()`，
  孤儿占位不会白占 24h 额度。
- 修正账号桶归一：`quota.check_quota()` 过去把 `account_key=""` 原样透传，读的是空桶，
  而 `worker` 写账本写的是「生效账号」桶——未确认永远算成 0。现在空串一律归一到
  `active_account_id()`。
- `/api/tasks` 的响应指纹加入 `count/pending`：账本变了而任务状态没变时也会重建响应，
  界面上的额度数字不会停在旧值；额度提示会注明「其中 X 篇上传中/结果未知」。
- 额度缓存键三种写法（账号 id / 生效账号 / `_active`）全部清掉，避免 180 秒旧数字。

**问题二：加入任务后队列不会立刻刷新显示任务。**
`pollTasks()` 开头有「上传文件时不抢带宽」的短路 `if (state.uploading) return;`，
而提交完成后的那次 `await pollTasks()` 又发生在 `finally` 把 `state.uploading = false`
之前——于是本次刷新被自己短路掉，用户要等下一轮自然轮询（退避后最长 20 秒）才看到任务。

- `pollTasks(force)` 增加 force 参数，上传期间的强制刷新可以穿透守卫。
- 新增 `prependTasks()`：`/api/publish` 返回的任务**本地立刻插到队列顶部并重绘**
  （多文件逐个入队，每传完一个就显示一个），不等服务端轮询。
- `finally` 里先 `state.uploading = false`，再 `await pollTasks(true)`。
- 队列里有 `uploading / queued / waiting_schedule` 任务时不再退到 10/20 秒轮询
  （最多 5 秒），投稿完成那一刻也能马上看到。
- 新增 `tests/verify_v106.py`（28 项）：账本状态机、模拟B站入库延迟下的越界验证、
  账号桶归一、缓存即时 +1、worker 三种收尾、前端守卫与版本号同步。

## 一、这是什么

一个**跑在自己电脑上的 B站投稿面板**（本地 Flask 服务 + 浏览器单页前端）。把视频拖进浏览器、填标题/分区/标签、排进队列，软件按**单线程顺序**帮你投出去，带进度、日志、失败重试、24h 额度把关、定时发布、多分P、合集、话题、仅自己可见、扫码登录等能力。

- 多账号：可登记多个 B站账号，按任务指定投放账号，额度/节流/风控**按账号隔离**。
- 单一上传通道：内置官方接口（无需额外软件）。v105 起移除 biliup CLI，见第〇节。
- 私有：Cookie 只存在本机 `data/config.json`（权限 0600），不上传任何地方。

## 二、核心架构

| 层 | 模块 | 职责 |
|---|---|---|
| 入口 | `run.py` | 解析参数、启动 `create_app()`、注册退出收尾（`worker.shutdown` 把 uploading 标为已中断）、SIGTERM 转 SystemExit |
| Web | `server.py` | 所有 HTTP 接口 + 静态页；维护**统计缓存**（workbench 按统计日缓存 / archive 90s 缓存 + 投稿作废）、**响应体指纹缓存**、图床代理、账号头像预热 |
| 队列 | `worker.py` | 单线程 `_loop` 顺序取任务；负责 10 分钟窗口节流、风控/限流冷却、**24h 额度把关与封禁等待**、定时稿调度、卡死看门狗、合集后台挂载 |
| 额度 | `quota.py` | `nav` 登录态、创作者中心三状态并发拉取、账本合并、封禁状态机 `quota_ban_until` |
| 账本 | `ledger.py` | 每次投稿成功即落地一条（带 BV/aid 身份键、按账号分桶、保留 26h），填补 B站列表入库延迟 |
| 存储 | `store.py` | `config.json`（含多账号 + 迁移自愈）+ `publish.db`（WAL）+ 模板；配置/任务指纹缓存 |
| 通道 | `channels/` | `official`（bilibili-api-python）唯一通道；v105 起固定为 official |

**设计要点**：用单线程顺序上传是刻意的（B站同账号并发不友好，也避免额度统计打架）；所有阻塞等待都走可中断 `Event.wait`，取消/暂停能立刻生效；进度落库按「≥1s 或 ≥1%」节流，避免分块回调压垮 SQLite。

## 三、投稿主流程（`worker._handle`）

1. **定时稿分流**：`local` 本地候到点自动上传；`bili` 距发布 ≥10 分钟交 B站定时、不足则本地候到点、超 15 天直接 fail、过期超阈值按设置拦下。
2. **10 分钟窗口节流**：按**账号**独立计算（A 占满窗口不拖 B）；占满则登记该账号为「暂时跳过」，主循环改取别的账号。
3. **24h 额度把关**：复用 10s 内新鲜结果或现查。三种分支：**未登录 → fail**；**数据不全且非封禁期 → 人工暂停**；**额度满/封禁 → 自动暂停排队（留 queued，不标红）**。
4. **补齐封面**：无封面则从首视频抽帧；抽不到 → fail。
5. **上传**：v105 起固定走内置官方接口（`_choose_channel()` 返回 `official`），不再做通道探测。
6. **上传 + 记账**：成功后立刻写账本（未确认 +1）、记节流窗口、清限流冷却；成功后异步挂合集（后台单线程，不卡主队列）。
7. **失败处理**：限流（-702/406/429）与风控（-352/-796/-412/验证码）分两类，前者等 1/10 分钟自动续投**不消耗重试次数**，后者按账号冷却；连续限流达阈值 → `rate` 暂停待人工；其它异常按 `max_attempts`（默认 2）重试。

## 四、24h 投稿封禁规则（重点）

**真实规则**：近 24h 投稿数一旦达到 **n+1**（上限 50 即 51）→ B站**封禁投稿**；封禁期内即使老稿滑出、额度降到 n 以下**也不能投**，必须等窗口内稿件全部过期、**额度归 0** 才恢复。

因此「封禁 24 小时」与「额度归零」在数据上等价，截止时刻取 **`max(ctime) + 24h`**（最新一篇投出时触发 n+1，从它起算 24h 后全部过期）。

### 封禁状态机（`quota.quota_ban_until`）

| 状态 | 触发 | `ok` | 恢复条件 |
|---|---|---|---|
| 正常 | `count < limit` | True | — |
| 刚好满 n | `count == limit` | False | 等最早一篇滑出，`next_release_at = min(ctime) + 24h` |
| **封禁** | `count > limit`（n+1） | **False（恒定）** | `count == 0`，即 `max(ctime) + 24h` |

**关键实现约束**（最易漏处）：

- 封禁截止 `quota_ban_until` **落盘到 config**，重启/升级/接口抖动都不丢、不误放行。
- 封禁期内 `check_quota()` 的 `ok` 恒为 False，**不看当前 count 是否已降到上限以下**。
- 只有 `count == 0` 才清除封禁；名义截止已过但稿件还在时**顺延 60s 复查**，不误放行也不永久卡死。
- 接口抓不全（`incomplete`）时**沿用旧封禁值**，不新设也不清除；宽松模式/异常分支同样不能绕开。
- `worker._quota_with_ledger()` 缓存合并后**必须再过一次封禁判定**，否则 `count < limit` 会把封禁覆盖成放行。

## 五、「额度恢复后自动继续投稿」开关

设置 →「额度与重试」→ **额度恢复后自动继续投稿**，对应配置 `auto_resume`（默认开启，`/api/config` 白名单内）。

### 暂停原因分型

| 原因 | 谁写的 | 自动恢复 |
|---|---|---|
| `""` | 运行中 | — |
| `manual` | **用户主动点暂停** / 额度统计不完整待核对 | ❌ 绝不自动开投 |
| `boot` | 部署/升级时写入的保护性暂停 | ✅ 受 `auto_resume` 控制，开启即自动解除 |
| `quota` | 额度满 / 24h 封禁自动暂停 | ✅ 到解封时刻自动复查续投 |
| `rate` | 连续限流待人工核对 | ❌ 需人工点继续 |

**原则：用户主动的暂停永远优先。** 开启 `auto_resume` 只解除部署保护性的 `boot` 暂停，不会把用户自己按下的 `manual` 暂停悄悄解除；手动暂停落盘，重启后依然是暂停。

### 启动自动恢复链路

`start()` → 读 `paused_reason` → 若为 `boot` 且 `auto_resume` 开 → 清 `boot` 保护 → worker 现查额度 → 检测到封禁 → `pause_for_quota()` 转 `quota` 等待，落盘 `quota_resume_at` → 到点复查额度归零即 `pause(False)` 续投。

## 七、部署与备份

- 数据库是 **WAL 模式**：只复制 `publish.db` 会丢 `publish.db-wal` 里的新任务，**备份/迁移必须整目录复制**（`publish.db` + `publish.db-wal` + `publish.db-shm`）。
- 部署时通常会在 `data/config.json` 写入保护性 `paused_reason: "boot"`，配合 `auto_resume: true` 让启动后自动恢复（检测到封禁则转入 `quota` 等待）。

## 八、已知限制

- 队列单线程顺序上传，未做并发。
- 官方接口通道依赖 `bilibili-api-python`，B站接口变动可能需升级。
- 定时发布能否用取决于账号是否具备 B站定时权限；>15 天无法定时。
- 只处理本机文件上传，不做远端拉取/转码。
- v105 起只提供内置官方接口一条上传通道，不再支持 biliup CLI。
